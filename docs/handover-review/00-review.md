# 交接包审阅报告

修订 HR-1；日期 2026-11-17。源码位置均相对[原包根](../../source-snapshot/mdagent-handover-review-20261117/MDagent-subsystems-handover-20261117/README.md)。行号为本次交付字节的定位；结构化定位另见 findings.json。

## 1. 总体判断

设计方向合理，材料较丰富，源码与测试足以支持继续开发。当前不足集中在“接手者能否按说明无歧义、安全地复现和改造”，并非缺少更多概念性方案。

| 维度 | 判断 | 依据及含义 |
|---|---|---|
| 架构职责 | 基本合理 | UKB 管知识，v3 管任务证据，双门管方案，一致性层管声明与实现对照；四者不能互相代替科学验收 |
| 知识写入 | 有可复用实现 | propose、预审、内容摘要绑定审核和版本读取已存在；需要明确机器管理员权限与人工决定边界 |
| 证据与执行 | 有较强机制基础 | 单次许可、START_UNKNOWN 对账、输入封存、知识重验、不可变工件；真实执行链未随包验证 |
| 方案写入 | 不完整 | 缺原子替换和并发契约；调用方摘录文字不足以证明用户授权 |
| 一致性检查 | 有效但覆盖有限 | LAMMPS 静态检查可复用；空/未知判定的 PASS 漏洞须修复；不支持部分必须显式暴露 |
| 独立部署 | 部分成立 | 单元测试可复测，初始化、路径、依赖和外部适配仍有缺口；不能称四系统生产能力全部独立完备 |
| 文档和证据 | 多而未充分收敛 | 历史版本与当前路径混列，测试通过口径不精确；缺统一 action 契约、恢复演练及可重放冒烟 |
| Pi 通用性 | 需要边界适配 | Python 领域实现、旧阶段枚举、dsh 插件不能整体装入通用内核 |

保留的优点：逐文件哈希及来源记录；明确运行库/凭证不分发；测试与案例同时交付；主动披露前缀匹配和审阅截断；明确 PASS 不等于物理结论；公开 Null 接口和真实模型/求解器未验证。修订应延续这种事实分层。

## 2. 审阅方法和限制

检查包清单、入口及全部文档索引，重点阅读四系统的当前设计与相关历史审计；沿关键入口核对配置、写入、审批、审阅、状态、备份和执行调用；完整重跑包内自动套件，并对高影响边界做 8 项隔离探针。

这不是逐行穷尽审计，也没有对全部历史论文/科学规则作物理正确性背书。未访问生产库、未调用真实模型、未启动真实求解器或 HPC 作业。本轮未复测包内声称的手工 MCP/Web 冒烟，不能把它们算作本轮通过。

## 3. 问题清单

P1：在受影响路径投入使用或集成前修复；P2：工程交付与维护完整性问题。优先级针对该场景，不表示已发生生产事故。下列“源码确认”与“动态复现”明确区分。

### HR-01 / P1：多个数据根可能指向不同知识库，快速开始不能连续照抄

证据：`src/evolution/kb/adapter.py:117` 与 `src/design-review-layer/review_layer/ukb_store.py:57`。只设置 `MDSIM_DATA_ROOT` 时，前者可使用自定义数据根，后者仍走包内默认库；PROBE-06 已复现。`MDAGENT_UKB_ROOT` 与 `REVIEW_UKB_ROOT` 也没有共同的冲突拒绝机制。

README §3.2 先 bootstrap 再 init，但 `ukb_store.py:106` 对已初始化库退出；注释虽说二选一，bootstrap 路径仍缺保存供校核层使用的人类管理员凭据的衔接。§3.3 验证命令在连续执行前面的 `cd` 后也不在包根。

影响：检索和发布可能操作不同库，首次部署中断。修订：统一解析结果及显式冲突检查，给出一个完整初始化主路径，所有命令声明 cwd；已有库路径不得靠重复 init 修复。落实 HR-W01、HR-W06。

### HR-02 / P1：验证脚本未真正隔离运行库，清理目标与令牌创建位置不一致

证据：`tools/run_verification.py:60` 的 `_provision_ukb` 只设置 `REVIEW_UKB_ADMIN_FILE`，继承外部 `REVIEW_UKB_ROOT`。PROBE-07 用模拟子进程证明外部根会进入初始化命令，没有访问外部真实库。

令牌写到 `store.parent/admin.json`，finally 却清理 `design-review-layer/ukb_admin.json`；还可能删除本非本次创建的后者。初始化中途失败时 `provisioned` 尚未置真，清理不会执行。脚本也会覆盖原验证日志，结果不能保持原始交付证据不变。

影响：开发者直接运行验证脚本可能触及配置的外部根，留下凭据或破坏已有凭据文件；“不污染包内数据”的承诺不成立。修订：专用临时根、显式环境、精确创建清单、异常清理、外置结果目录。落实 HR-W01；本轮只在一次性副本运行原脚本。

本轮完整复测实际发现遗留 `src/data/admin.json`，详见 evidence/recheck.json；仅登记路径，没有读取或分发其中的令牌，临时副本已自动清理。

### HR-03 / P1：按前缀找算例会串案

证据：`src/mcp/md_proj_mcp.py:135`；PROBE-01 请求 foo，返回较新的 `foo_bar_20260102_000000`。这是原包已披露且本轮再次复现的缺陷。

影响：后续读写/确认可能命中另一算例。修订：使用项目、算例、运行三段身份定位；兼容旧目录时只允许精确语法匹配，再校验工件内部身份；歧义不得选“最新”。落实 HR-W02。

### HR-04 / P1：方案保存非原子，审计失败仍可报成功

证据：`src/mcp/md_proj_mcp.py:171` 使用 `open(...,'w')`；PROBE-02 模拟写入中断后原 JSON 变成单字符 `{`。写入口没有贯穿重读—比较—写入的任务锁/CAS。`_audit:105` 捕获异常只记日志，调用发生在方案保存之后。

影响：磁盘/进程异常造成原方案损坏，多调用方覆盖更新，成功状态没有可靠审计链。修订：锁内重读，精确版本校验，tmp+flush/fsync+replace，持久操作日志协调审计；审计待对账时不颁发可消费确认。落实 HR-W02。并发丢失更新和审计故障为源码确认，未声称本轮复现了实际并发事故。

### HR-05 / P1：审阅输入硬截断使结果覆盖范围不可证明

证据：`src/mcp/design_review.py:234`；intent 仅取前 6000 字符，最多两个输入文件、每个前 3000 字符。PROBE-05 的关键参数尾部标记消失。原包披露了 intent 截断，但输入文件数量和长度限制也需纳入治理。

影响：模型可能对没有看到的关键内容给出通过。修订：输入闭包摘要、范围/分块清单、必需覆盖检查与预算失败；只有完整覆盖的审阅可作门禁依据。落实 HR-W03。

### HR-06 / P1：空检查及未知判定被汇总为 PASS

证据：`src/design-review-layer/review_layer/review.py:18` 的最终 else；PROBE-03、04 分别为空列表与 `unsupported` 判定，结果均 PASS。

影响：检查器未产出有效结论也能形成成功报告。当前正常解析器通常产生检查项，本轮证明的是汇总函数的边界缺陷，不声称已有正常 case 被错误放行。修订：校验枚举、非空与必需检查覆盖；结构不合法不得出可用 verdict，覆盖不足至少 REVIEW。落实 HR-W04。该修复属于确定性结果校验，不向“零政策规则”层注入新的物理阈值。

### HR-07 / P1：前置终审只要求非空摘录，缺可信人工决定凭据

证据：`src/mcp/md_proj_mcp.py:638` 和工具 schema `:1054`。PROBE-08 在隔离 DESIGNED 工件上提供测试文字即得到 CONFIRMED；没有人工事件或内容摘要校验。

影响：CONFIRMED 最多证明调用方提交了一个声称的摘录，不能证明用户批准了当前版本。v3 的 `human_authority.py` 是另一路机制，此发现不等于已绕过 `sim_exec` 执行许可。修订：宿主可信决定入口签发绑定内容、身份与作用域的记录，普通模型工具只引用决定。落实 HR-W05。

### HR-08 / P2：旧状态机、v3 状态与通用状态的权威关系不清

证据：手册 §5.2 仍列 `stage_state` 为状态机；`src/mcp/md_mcp.py:883`～898 的阶段判断与状态查询已转发 v3。旧 `stage_state.py:34,67` 与 `evidence_v3/store.py:154,208` 使用同一类 `memory/tasks/<id>/state.json` 路径但 schema 不同；旧 loader 未拒绝 v3 schema，v3 loader 对旧 schema 限写。手册 §4.3 工件布局少了 v3 实际 `artifacts/` 层。

手册“request_id 幂等重放”也不能推广为全部 action：例如 `evidence_api.py:92`～105 的 plan/evidence 没有传 request_id；`revision` 表示内容版本，`state_seq` 才是更广泛状态变化计数（service.py:114～131）。

影响：接手者可能误以为旧门与新门可并行写同一任务，或把所有失败都作为可安全重试。修订：生命周期表、逐 action 契约、旧写禁用和显式迁移；Pi 只保留 K6 权威。落实 HR-W06。本轮没有证明生产入口仍可直接调用旧状态写入。

### HR-09 / P2：知识不可用的降级语义与总体 fail-closed 承诺不一致

证据：`review_layer/common_issues.py:14` 捕获异常后读本地 JSON；`discovery.py:30` 在 UKB 不可用时用本地基线。`sources.py` 不仅有 Null，也有 Seed/DataRoot 实现，但默认配置及结果缺少统一能力披露。

影响：演示可继续工作，但报告不能让消费者区分“生产知识已读取”“本地演示数据”“没有接上证据”。修订：显式 mode、sourceRef、版本、读取范围、降级原因；生产必需知识不可用时阻塞相应 gate。保留显式离线演示能力，不笼统删除降级。落实 HR-W07。

### HR-10 / P1：SQLite 备份不等于完整知识库恢复包

证据：`src/ukb/ukb/api.py:184` 调用 `core/maintenance.py:106` 的 SQLite backup；正文文件另存 `root/blobs`（api.py:16）。现有 backup 作为 SQLite 备份本身是合理的，缺的是包含原文 blob 的完整恢复契约和演练。

影响：只带走 .sqlite 可恢复索引/元数据，但可能无法恢复文档原文。修订：一致性数据库快照+其引用 blob 清单+哈希+注册表/schema版本+独立凭据恢复步骤；恢复到新目录验真后再切换。落实 HR-W07，不把 token 明文混入通用导出包。

### HR-11 / P2：测试统计、冒烟回执和能力声明需分层

原始记录是 597 个 unittest，其中 8 跳过，实际成功 589；Node 29 成功；合计 626 个登记测试、618 成功、8 跳过。README 的“626 全绿/597 全部通过”不够准确。5 个端到端场景是独立计数，不能再并入相同分母。4 项手工冒烟未包含在自动脚本，不能由 all_ok 推导它们本轮通过。

脚本 `_unittest_count` 读不到计数时仍可按退出码判断成功；超时或缺命令会中断，缺少完整失败回执。真实模型、审阅质量、求解器、Linux 权限/锁及恢复未被此测试数覆盖。修订：逐层计数、预期套件清单、零测试拒绝、跳过理由及补跑环境、冒烟脚本和原始协议/HTTP回执。落实 HR-W01、HR-W08。

本轮完整复测出现 1 个测试错误：`test_md_mcp_contract.py:148` 的子进程文本解码未指定 encoding。在验证包装器设置 `PYTHONIOENCODING=utf-8`、Windows 父进程 locale 仍为 GBK 的环境中，输出解码失败，继而访问空 stderr 触发 TypeError。后续去掉 stdio 编码覆盖、使用本机原生 locale 仍复现，完整 UTF-8 模式则 12/12 成功；属于编码可移植性缺陷，不可据此断言原作者环境的历史测试造假。针对性复测见 03 文档。另，原脚本只更新 RESULTS.json 和 logs，不更新 RESULTS.md；重跑后 Markdown 仍可能显示旧的“全部通过”。

### HR-12 / P2：源码来源可核字节，但不足以重建可维护发布基线

正面事实：376 文件清单一致。缺口：两工作树未提交改动混合，变更说明不等于逐项 patch；`package_manifest.py` 无上游参数重跑会把来源重标为 handoff-package；缺依赖安装/兼容矩阵，numpy 必需但无锁定安装入口；旧 SANITIZATION/NOTICE 描述的是更大上游包，并非当前 377 条目的内容清单。

修订：冻结交付快照与摘要，建立独立集成提交和补丁账；保持来源字段，增加本轮新增来源；区分实际分发与仅引用第三方；保存现有许可证，并在迁入目标仓前核对目标用途与授权。当前包许可明确为 PolyForm Noncommercial，不能随迁移默认为 MIT。未随包携带的旧 NOTICE 文件项不构成本轮已发现该文件被分发的证据。落实 HR-W08。

## 4. 建议的接受范围

可以接受：作为参考资产和修复起点；UKB 独立审核/检索机制、v3 证据执行边界和 LAMMPS 检查器可有选择复用。

暂不能接受：前置终审具有可信人工授权保证；四系统全部 fail-closed；任意 action 都可幂等重试；数据库备份即完整恢复；测试全绿即真实科学验收；直接整体迁入 Pi 即具备跨领域能力。

这些限制已转成后续文档中的实现任务与验收，不以“继续补文档”替代必要代码修复。
