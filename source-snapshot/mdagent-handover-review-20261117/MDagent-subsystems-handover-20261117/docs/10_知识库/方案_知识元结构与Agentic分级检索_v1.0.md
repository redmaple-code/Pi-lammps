## 1. 决策摘要

不增加 L4/L5 来延长一条混合层级，也不将知识库迁成向量 RAG。保留细粒度原子记录作为事件/观察和溯源材料；将“一个可独立复用的完整经验”定义为 agent 的知识消费单位；来源、证据关系、适用条件、审核生命周期、分类标签和检索投影分别表达。检索采用受控路由、轻量候选筛选、完整单元读取、适用性判断和必要时证据追查的 agentic 分级流程。

知识仍写入既有底座与晋升通道。索引、场景、知识卡和可读规则都是可重建服务视图，不是新事实源。当前 `review_experience` 与运行时 `atoms` 的代码契约有差别；本方案中的完整知识单元是目标契约，落地前必须保证消费者能呈现全部关键语义，不可只增加无人读取的字段。

## 2. 何谓过度切分

原子化适合准确记录单次观察，不代表单个 atom 就足以支持跨任务复用。若前提、判断、行动、结果和反例被分别存放，而检索只取到其中一条，语义会丢失；`refs` 只能在消费者实际追查时恢复上下文，不能自行补回缺失语义。

切分/组合依据应是“能否独立适用与治理”，而非字数或句子长度：

- 若多个断言总是共同成立、共同适用、共同审核和共同撤销，保持在同一知识单元中。
- 若断言可在不同条件下独立成立、证据强弱不同或生命周期可能分叉，应拆成不同单元，并用明确关系连接。
- 原始观察可以细分为多个 atom，但必须能通过稳定 ID 或关系重组为同一案例/经验上下文。
- 同类签名只表示检索线索，不证明原因、条件或修复相同；聚合不得消掉反例、冲突与来源差异。
- 摘要、卡片标题和检索片段不可替代完整知识单元；模型蒸馏不得新增原始证据没有的机制或数值。

因此，“观察/事件记录”与“可复用知识单元”是不同对象。一个知识单元可引用多条 atom、案例和来源，也可以只引用一条；不要求所有 atom 都晋升。

## 3. 对象结构与现有资产映射

| 对象 | 语义职责 | 现有资产/落位 |
|---|---|---|
| Source / Evidence | 原始文档、日志、产物或外部材料；记录来源、版本和可核查位置 | LEDGER、任务产物、外部语料及已有 refs；外部材料仍是未验证来源 |
| Observation / Event | 某个时间、任务与条件下发生/测得的事实，不隐含普遍性 | `atoms.jsonl` 与 L0 事件；atom 是细粒度账目，不自动成为 active 规则 |
| Case / Episode | 有边界的一次任务经历，串联目标、上下文、动作、结果和处置 | 既有案例/任务工件及其引用；任务证据仍属任务域 |
| Knowledge Unit | 在明确范围内可复用的完整主张、经验、程序或约束 | 已审核内容优先走 `review_experience`；候选观察仍走既有 `record_atom` 与人工晋升路径 |
| Projection | 为浏览、导航、聚合或检索生成的视图 | `scenarios.json`、SOP、knowledge cards、分类目录及未来轻量索引；均可重建 |
| Retrieval Record | 某任务检索了哪些知识、判定适用/不适用的依据及使用结果 | 需要留痕时落任务工件；不是长期知识正卷 |

这些对象不是单向 L0→L5 毕业阶梯。观察可永久保留为观察；案例可不抽象；多个证据可支持一个知识单元；知识单元被撤销时其原始证据仍保留。

## 4. 推荐知识单元契约

一个单元围绕一个可独立复用的主张。建议的通用字段如下，具体字段应兼容现有 `review_experience` 消费面并通过其人工审核，不得另建平行知识库：

```json
{
  "id": "ku-<stable-id>",
  "kind": "lesson|methodology|boundary|procedure|convention|capability|...",
  "statement": "完整、可引用的结论或建议",
  "scope": {"topic": [], "method": [], "ops": []},
  "conditions": {"key": "value"},
  "rationale": "依据与推理边界",
  "action": ["建议动作或检查"],
  "outcome": "实际观察到的结果；未实测则明确标为未知",
  "limitations": ["不适用条件、反例或尚未验证项"],
  "evidence": {"supports": ["atom:<id>", "case:<id>"],
               "refutes": [], "sources": ["source:<id>"]},
  "relations": [{"type": "related|supersedes|depends_on", "target": "<id>"}],
  "provenance": {"origin": "human|observation|literature|system", "recorded_at": "..."},
  "review": {"status": "candidate|canary|active|revoked|superseded",
             "reviewed_by": "...", "reviewed_at": "..."}
}
```

字段语义必须分开：

- 证据支持/反驳描述主张与依据的关系；不能压成一个不透明的 confidence 数值。
- 适用条件描述边界；缺条件不代表通用适用。
- 审核授权与生命周期描述是否允许消费；用户确认/人工复核与来源置信不是同一属性。
- `topic`、`method`、`ops` 是分类/路由轴，不是审核状态、证据等级或检索分数。
- 检索排序只表示对当前任务的相关程度，不表示事实真值或权威性。
- 冲突主张应并存并连接支持/反驳关系，等待判断；不得由更新时间、多数票或排序分静默覆盖。

`review_experience` 当前既有字段包括 `statement`、`conditions`、`rationale`、`remediation`、`refs`、`provenance`、`status`。可按上述语义承载首期知识，但若 `limitations`、反证关系或结果未被读取/呈现，就要把它们完整写入当前可消费字段或先扩展消费者契约。未知字段被 JSON 接受，不等于会进入 AI 简报或仲裁。

## 5. 生命周期与晋升

建议的治理语义：

1. 候选：记录观察或提案，可搜索并用于调查，不可单独作为跨任务强制规则。
2. 试用（canary）：可向 agent 提示，必须显式标注试验性；不能单独支撑 hard 决策。
3. 有效（active）：经既有人工闸批准后，在声明的适用范围内供消费者使用。
4. 取代（superseded）：保留历史和替代链，不再作为当前建议；不能与“原事实错误”混为一谈。
5. 撤销（revoked）：由于证据或授权变化停用；保留审计记录并从有效召回中排除。
6. 隔离（quarantined）：schema、来源或完整性异常，不进入召回。

具体实现沿用各消费面的既有枚举（例如 `review_experience` 当前的 active/canary/revoked），跨包状态映射须明确且 fail-closed；在消费者尚不支持 superseded 前，不可仅新增该状态字段后假设旧知识已退出召回。

晋升继续使用“观察/record_atom → 提案与证据核对 → 人工批准/apply_proposal → 既有经验服务面”的单一通道。批准某种数据模型不等于批准每条新经验成为 active。回滚、撤销和取代都应保留来源并使各消费者语义一致。禁止通过直接写种子包绕过审批或新增第二经验库。

## 6. 小体量知识库的 Agentic 分级检索

本方案不切向量块、不建 embedding 库，也不要求 SQLite。小库优先使用现有 JSON/JSONL/Markdown 权威记录与可重建的关键词/标签目录；agent 按需读取完整单元和证据。

建议运行步骤：

1. 意图识别：把当前问题归纳为目标、对象、方法/操作面、关键条件、时间范围和风险；未知项保持未知。
2. 路由：用少量受控 topic/method/ops 标签及对象 kind 确定候选目录；候选标签只扩大搜索，不当作已认证分类。
3. 候选查找：在小型索引或全量元数据上用关键词、标签、条件和关系找到候选 ID。索引记录 ID、kind、简短标题、scope、conditions、status 和来源，不复制权威正文。
4. 完整读取：读取候选知识单元全文，不能只把 atom、摘要或片段作为最终知识输入；只向下追查与当前判断相关的 refs、案例或矛盾项。
5. 适用性裁决：比较当前任务条件与单元 conditions/limitations；active 且匹配时方可作为当前建议，canary 降级提示，候选/撤销/隔离按治理状态处理。
6. 冲突处理：并列展示相反证据与适用边界；无法化解时请求补证或人工裁定，不由“最新”自动胜出。
7. 回答与留痕：引用知识单元 ID 和必要证据 ID；涉及门禁/高风险时把检索集合、适用性理由和裁决写入既有任务工件。
8. 反馈沉淀：真实结果只先进入既有观察/任务记录通道；跨任务推广仍须人工审核晋升。

检索预算由任务复杂度和风险决定：简单问题可止于路由与完整单元；高风险或冲突问题再扩大到源证据和案例。排序函数可以用于相关性，但不得把“高分”当作证据质量或审核授权。

## 7. 现状差距与兼容边界

- MDagent `memory.py` 的 `record_atom` 把 `fact` 截至 400 字符；超长知识无法安全地靠多条互不关联 atom 表达完整单元。已确认的活动底座必须先检查此长度约束，短单元可暂以一个完整候选记录验证，长单元需后续扩展既有单一底座契约及消费者，不可静默截断。
- atom 结构没有独立 lifecycle/status；标签轴也不承担审核授权。经 `record_atom` 直接写入只适合候选观察/经授权的知识记录，不能伪称完成 review_experience 晋升。
- 旧 `knowledge_cards.py` 按 kind 聚合 facts，构建的是导航/浏览卡，不是每个知识单元的审核正卷；其摘要长度和引用数有上限。测试必须核对原 atom 的完整事实与 refs，不能仅以卡片生成成功判定语义完整。
- 上次知识审查所针对的缓存 MDagent main 未证实存在端到端运行时自然语言召回；本机 `sim-agent-runtime` 是独立运行时数据副本，测试它不等于证明服务器部署或所有 agent consumer 均已接通。
- 知识消费者应共用完整单元读取与生命周期解释；异步投影重建失败不得改动权威源，也不得制造“已生效”的假象。

## 8. 实施与验收建议

不在本次研究中迁移存储或开发新索引。后续实现按以下顺序：

1. 先为现有消费者建立对象/字段映射表，确认哪些数据是权威源、哪些是投影以及各消费者如何过滤撤销/取代状态。
2. 确定一份能被完整读取的知识单元契约，并用长度、缺字段、错误状态、缺失引用、相反证据、条件不匹配和超长内容做测试。
3. 统一检索入口为 agentic 分级读取，强制候选详情回读、来源回链和状态过滤；索引可删可重建。
4. 用小批通用知识做真实数据路径试写：核对写入函数接受、磁盘回读逐字节/字段一致、关键词检索能找到完整单元、派生视图不截断、原有记录数与内容保持不变。
5. 只有规模、延迟或并发证据显示现有线性扫描不足时，才评估 SQLite FTS 等轻量目录；不得因此改变唯一知识事实源。
