# UKB 召回率与入库准确率盲测（2026-10-31）

T-059 / EV-20261031-003。测试对象是生产测试库 `ukb_prodtest/kb`（58 条金属 MD 条目）。

## 方法

测试由四个独立的 AI 子代理完成。它们之间不共享答案，我也没有参与评判。

| 角色 | 能看到的 | 不能看到的 |
|---|---|---|
| 出题 | 58 条条目的标题和正文（导出时去掉了标签） | 标签树、库、源码 |
| 检索 A、检索 B（各 20 题） | 只通过 MCP 工具面访问库（`tools/prodtest/ukbcall.py`，会记录每次调用） | 标准答案、库文件、源码 |
| 投递 | 7 份原始材料（`submit_raw/`）；只通过 MCP 工具面访问库副本 `kb_submit` | 库文件、源码 |
| 评判 | 原始材料、10 条投递、标签树、类型表 | — |

题目共 40 道：症状类 13、做法类 13、事实类 10、库内无答案 4，其中 7 道需要 2 条以上条目才能答全。打分脚本是 `tools/prodtest/score_retrieval.py`，原始数据在 `ukb_prodtest/eval_*.json(l)`。

## 召回率（36 道有答案的题）

| 指标 | 结果 |
|---|---|
| 命中率（至少用到 1 条标准答案条目） | **36/36 = 100%** |
| 回答召回率（用到的标准答案条目 ÷ 应用到的） | **98.6%**；多条目题 92.9% |
| 回答精确率（用到的条目中属于标准答案或相关条目的比例） | **99.3%** |
| 选定范围内包含全部标准答案条目的比例 | 98.6%（唯一遗漏是 Q16） |
| 范围精确率（范围内属于标准答案的比例） | 17.9%：每题平均读 10.6 条（占全库 58 条的 18%），从中挑 1 到 2 条 |
| 库内无答案的题 | 4/4 正确回答 NOT_FOUND，没有凭空编造 |
| 误报"找不到" | 0 |
| 成本 | 每题约 0.9 次调用、读入约 5,300 字；工具调用 37 次（overview 11、read 21、catalog 1、read_original 2、must_read 2） |

唯一的漏召回是 Q16"新 EAM 势在使用前要检查什么"。答案分散在多个主题标签下，代理选的两个范围里缺了"输入脚本自查清单"那一条。

**结论的适用范围**：库只有 58 条，代理读一两个范围就能覆盖大部分内容。库规模扩大十倍以后，范围精确率和读取成本会成为瓶颈。另外，有些题的措辞和条目中的"情境"描述比较接近，检索 A 代理也指出了这一点，所以 98.6% 偏乐观。

## 入库准确率（AI 自主投递 10 条，由独立评判逐条判定）

| 维度 | 正确 | 小问题 | 错误 |
|---|---|---|---|
| 内容 | 7 | 3 | 0 |
| 类型 | 10 | 0 | 0 |
| 标签 | 2 | 8 | 0 |
| 值得入库 | 10/10 | | |

- 投递流程：先查已有内容，再投递。代理主动跳过了 5 类已有内容，其中一份故障日志与已有条目同源，因此没有作为新证据投递；另有一条走了"强化已有条目"。
- 内容方面的小问题：一处 setfl 示例与 `pair_style eam` 不匹配；版本条件写得过窄；把约化单位的步长填进了以 ps 为单位的条件键；强化条目引用的两个来源出自同一次运行，不能算独立证据。
- 标签方面的问题主要来自标签树本身：LJ 体系只能挂"金属 MD"领域，没有"相稳定/亚稳态"标签，也没有"截断与长程修正"标签，代理只好挂在熔点、热学这些相近的标签下。
- 评判发现一个三方都没察觉的语义问题：投递方运行时开了 `tail yes`，但参考答案没开，导致相关的 4 条结论适用条件不清。这正是需要 AI 预审和管理员审核把关的地方。
- 内部重复：有 3 条是同一个"亚稳固体"结论，分别写成了失败模式、经验和流程三种形式。
- 漏掉的知识：评判认为有 3 到 4 条可以入库但代理没有投，比如标准设计规则："冻结参考值前确认单相"。

按评判口径，**严格准确率**（三项全对）为 1/10；**可用准确率**（没有错误，最多有小问题）为 10/10。

## 测试暴露并已修复的工具问题

| 问题 | 修复 |
|---|---|
| `ukb_read` 传了错误参数名 `refs` 时被静默忽略，返回整库 58 条 | MCP 层按工具定义严格校验参数，未知参数返回 ARGUMENT_UNKNOWN 并列出可用参数，缺少必填参数返回 ARGUMENT_MISSING |
| 投递时漏了 `payload` 外层，报的是 Python 异常 `KeyError` | 同上，改为返回 ARGUMENT_MISSING |
| guide 里没有投递示例，代理靠试错才弄清 `source_type`、`note` 等字段 | `ukb_guide` 增加 `payload_examples`（new、文档文件、revise、reinforce 的完整结构）和定位写法说明 |
| `ukb_read` 输出冗长，两个检索代理都自己写脚本裁剪 | MCP 默认使用 compact 视图（同一范围 13.2 千字降到 7.0 千字，正文不变），需要完整信息时传 `view=full` |
| overview 的 `within` 参数格式没有说明 | 在工具描述中补了示例 |

单元测试新增 3 项，共 100 项通过。修复后重跑生产测试，65 项全部通过。

## 尚未解决、需要决定的

- 标签树要补："简单流体/模型体系"领域、"相稳定性"主题、"截断与长程修正"主题，以及无单位的时间步条件键。
- 生产测试批次里有 2 条来源错挂：邻居列表和 1 fs 步长这两条引用了 NPT 的 a0 注释。清理时一并处理。

## 第二轮：逐级暴露后复测（T-062 / EV-20261031-005）

所有者指出：检索应当逐级暴露，第一轮只给标签，多轮确认后才给完整内容。第一轮的实现是"传一个范围就返回范围内全部全文"，目录只是可选步骤，两个检索代理 21 次 read 调用、只调了 1 次 catalog，属于实现偏离设计意图。改为 §6.2 的逐级暴露并在 MCP 层强制后，用同一套 40 道题、另外两个全新的检索代理复测：

| 指标 | 第一轮（一次给全文） | 第二轮（逐级暴露） |
|---|---|---|
| 回答召回率 | 98.6% | 98.6% |
| 回答精确率 | 99.3% | 99.3% |
| 多条目题召回 | 92.9% | 92.9% |
| 库外题判无 | 4/4 | 4/4 |
| 读取完整内容的条目数（40 题合计） | 159 | **56**（-65%） |
| 每题暴露字数（所有工具返回合计） | 6,584 | **3,227**（-51%） |
| 其中完整内容（read） | 231,827 | **55,210**（-76%） |
| 每题工具调用 | 0.9 | 1.9 |

召回率和精确率没有变化，暴露的完整内容减少 76%，代价是调用次数翻倍：目录和读取多了一步。唯一的漏召回仍是 Q16。

第二轮代理反馈的问题以及处理方式：

- **目录被截断后没有说明怎么办。** 以前只提示"请缩小范围"，代理只能逐个主题试。现在提示里会列出可用来细分的标签和各自的条数，并在描述里写明"超出部分不显示、也不分页"。
- **子标签要展开才能看到。** 这是逐级暴露的有意设计。工具描述里已补充说明：父标签已经包含子标签，并会显示每个标签有几个子标签。
- **来源标签错挂、数值写在备注里。** 这是注入数据的问题，留到清理时处理。

修复后：单元测试 102 项、生产测试 70 项、审计 92 项全部通过。生产测试中 13 个下游问题按"目录 → 每次读 3 条"的方式全部命中，每题读取 0.5 千到 4.5 千字。

## 第三轮：精简文本输出后复测（T-063 / EV-20261101-001）

所有者认为第二轮每题 3,227 字仍然偏高。拆分来看：目录占 45%，全文占 43%，标签树占 12%。主要原因是每级都返回带缩进的 JSON，字段名、条目 ID、与所选范围重复的标签反复出现，真正用于做选择的标题只占一小部分。改动如下（只改 Agent 看到的 MCP 文本，结构化接口、审核台和预审不变）：

- **标签树**：一行一个标签，格式为"slug 名称(条数)+子标签数"；说明和别名默认不显示，传 `describe=true` 才给。topic 顶层从 2,389 字降到 394 字。
- **目录**：一行一条，格式为"#编号 类型 标题 ·额外标签"；目录内共有的标签和所选范围的标签不再重复显示；条目用会话内短编号 `#n` 表示。10 条从 1,862 字降到约 620 字。
- **读条目**：输出"字段: 值"行；案例和文献默认只给判断用的核心字段，复用细节（reuse、setup、findings、data_values 等）留到 `depth=full` 再给；同时去掉 ID、哈希、版本号。一个案例从 855 字降到 443 字。
- **原文读取与复用取出**也接受 `#编号`（第三轮代理曾因为不支持而报错）。

同一套 40 道题，换两个全新的检索代理：

| 指标 | 第一轮 | 第二轮 | 第三轮 |
|---|---|---|---|
| 回答召回率 | 98.6% | 98.6% | 97.2% |
| 回答精确率 | 99.3% | 99.3% | 100% |
| 多条目题召回 | 92.9% | 92.9% | 85.7% |
| 库外题判无 | 4/4 | 4/4 | 4/4 |
| 每题暴露字数 | 6,584 | 3,227 | **677** |
| 读全文条目（40 题） | 159 | 56 | 51 |
| 每题调用 | 0.9 | 1.9 | 1.4 |

每题暴露量比第二轮再降 79%，比第一轮降 90%。召回少了 1 题：Q13 用到两条中的一条，答案仍然正确，但没有引用弹性常数流程那一条。Q16 与前两轮一样漏了自查清单。召回率下降在 1 题的波动范围内，不能确定是格式造成的。

第三轮代理反馈的问题：

1. 短编号与列目录的顺序有关，跨会话不稳定。这是有意为之，引用时应改用 `entry_id@rev`，需要时用 `format=json` 获取。
2. "纠正"和"经验"两类内容有重叠，需要清理时合并。
3. 如果只按 topic 选范围，会漏掉 method 面的条目。
4. 来源标签错挂（已知的注入数据问题）。
5. `must_read` 为空：测试口径没有配置必读条目。
