## 二、冗余二：两个评估引擎重叠

`evolution/assessment.py`（278 行，快检 PA1-PA3 / RA1-RA4）与 `evolution/deep_review.py`
（204 行，方法论维度）在实弹中同时运行，且：

- PA1（步长）≡ `mdev-general-dt`（同一 dt* 判定，两份实现）；
- PA3（依据完备）≡ R17（完全重复）;
- PA2（验收可量化）与 R10 意图重叠。

**处置**：删除 PA1-PA3；RA1-RA4（温漂/RDF/密度/复现）并入 deep_review 的结果相位维度。
概念从"两层评估"收敛为"一个评估引擎"。

## 三、精简目标（v3）

1. 规则 **19 → 11**：R1(含 R7) / R2(含 R3/R6) / R4(含 R12) / R8 / R9 / R10 / R13(含 R11) /
   R14 / R15(含 R5) / R17 / 配置机检(正名)。拦截行为零丢失，仅收拢原因码。
2. 引擎 **2 → 1**：assessment.py 收缩为结果相位物理检查器（或并入 deep_review）。
3. 知识数据 **不动**（16 条是内容不是结构，每条有出处）。
4. 报告页签 **11 → 7**：系统全景 / 生效点与拦截 / 案例总表（折叠）/ 复核与教训。

预计生产代码 1,992 → **约 1,300 行（-35%）**；工作量约半天，需全量单测（118 项）+
八案例实弹回归。

## 四、明确不动的东西（非冗余）

- 状态机（stage_state）、证据门核心（stage_gate 的校验骨架）、配置机检（config_check）、
  数值对账（content_check）、深度分析（deep_review）、知识数据（review_experience）；
- 测试规模（约为生产代码 0.65 倍）属健康比例；
- 演示层（驱动/报告/客户端/审计桥）是测试工装，不计入生产系统。

## 五、取舍原则

- 合并规则时保留原原因码作为别名（`R3:config-*` 等沿用），避免历史 gate-log 断链；
- 每次合并必须跑全部单测 + 八案例实弹，拦截行为逐条对照（R15/R3/R9 三类触发点不得变化）；
- v3 完成前，本提案仅作存档，不改变现有 16/19 已上线状态。
