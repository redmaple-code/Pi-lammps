## 3. 信息架构（实验背景 × in 文件 的索引）

单页三段式，左侧「背景与审核」，右侧「in 文件原文」：

```
hero          标题 + 一句话说明 + 5 项统计（案例/审核项/一致/偏离-缺口/待核）
case tabs     5 个案例（含放行/阻断状态点），吸顶
workspace     左：实验背景（字段表，每行带 intent 字段路径）
                门报告结论（硬/存疑/警示/审阅层故障 + 层级）
                逐项审核（可筛选；每条=判定+层级+维度+行号+原声明+依据+字段路径）
              右：in 文件原文（逐行编号，逐字复制；多文件可切换；点审核项定位并高亮行）
                溯源（intent.json / in.case / log.lammps / gate 报告路径）
method        判定四档语义说明
```

判定四档只描述「方案声明」与「文件写法」之间的关系，不重判物理对错：

| 判定 | 含义 |
|---|---|
| 一致 match | 背景声明与 in 文件写法相符 |
| 偏离 deviation | 两者数值或口径不一致，以 in 文件为准回改方案 |
| 缺口 missing | 背景声明在 in 文件中没有对应实现 |
| 待核 check | 需补记录，或方案内部自相矛盾，暂不能判 |

## 5. 本页揭示的索引错位（页面核心价值）

这些不是页面的判断，而是「方案声明 vs in 文件」两处文本的真实差异，均有行号可查：

1. **a3 系综声明与脚本相反**：intent 两段写 `nvt`，`in.case:19` 是 `fix 2 all npt ... iso 0.0 0.0 1.0`
   并输出 `v_a`/`v_rho`。审阅层据此判的两条 hard（NVT 下体积恒定、a0/ρ 不可测；对照成恒真回声）
   **对方案成立、对实际脚本不成立**。这是最典型的「审阅对象错了」。
2. **a3 缺 minimize**：方案 `ensemble_sequence[0]=minimize`，in 文件与日志均无 minimize，
   `create_atoms` 后直接 `velocity`+`nvt`。
3. **a1 体系规模 500 vs 108**：方案声明 5×5×5/500 原子，`in.case:6` 是 `region 0 3 0 3 0 3`（108 原子），
   日志「Created 108 atoms」证实。
4. **p1 目标覆盖 1/4**：该 in 文件只有一个 xy 剪切（C44），C11/C12/a0 无对应脚本。
5. **p2 取向覆盖 1/3**：只有 `orient z 1 1 1`（111）面，案例目录无 (100)/(110) 脚本。
6. **p3 三处口径不一致**：总步数 220000≠210000、升温速率 20≠10 K/ps（注释级）、
   原子数 720（material_model）vs 1008（abstraction）vs 720（in 文件）、盒 z 28.55≠40 Å。
7. **p3 审阅层 DEGRADED**：两次输出非合法 JSON，被 fail-closed 拦为 REVIEW-INFRA；
   但 in 文件索引不依赖 LLM，仍可逐项核对——这正是双门分工的现场证明。

  （前者无对应 in 文件、后者工件在工作区外）。

  页面把两者分列显示，未做合并。
- 官网仓库有独立 git，本次改动**未提交**（用户未要求提交）；工作区本身不是 git 仓库。
